# DailyDutch — Lessons Learned

Version 1.0 · 28 October 2026
Add each team member's own points before handing in.

## What went well

| # | Observation | Why it worked | Keep doing |
| --- | --- | --- | --- |
| 1 | Thin working slice first (format + 3 lessons + review) | Proved the idea before scaling content | Start every project with an MVP |
| 2 | Automated content validator | Enforced the core quality rule on 1,822 words without manual checking | Automate the rules that matter most |
| 3 | Open data for vocabulary (frequency list + Wiktionary) | Most useful words first, articles/plurals/forms ready | Look for existing data before writing by hand |
| 4 | Written authoring guide | Made writing 117 lessons consistent and repeatable | Document the process, not just the code |
| 5 | Static site, no backend | €0 cost, no privacy issues, simple deployment | Choose the simplest architecture that meets the need |
| 6 | Clear out-of-scope list | No time lost on accounts, sync or native apps | Write down what you will NOT do |

## What could be better

| # | Observation | Effect | Next time |
| --- | --- | --- | --- |
| 1 | Lessons 4–120 were written fast | Language quality not yet verified | Plan review time per batch of lessons, not at the end |
| 2 | Deployment left to the end | Definition of Done not met at presentation time | Deploy early (after MVP) and keep deploying |
| 3 | Planned dates not recorded at the start | Hard to compare planned vs actual | Baseline the schedule when the charter is approved |
| 4 | Little user testing during build | Feedback comes late | Put a live link in front of test users from week 1 |
| 5 | PM documents written after the build | Documents describe rather than steer | Write charter + risk register before coding |

## Recommendations for future projects

1. Baseline scope, schedule and risks at kickoff and update them weekly.
2. Deploy the first working version immediately; use continuous deployment.
3. Pair automated checks with human review for content quality.
4. Time-box polishing; protect time for testing and documentation.
